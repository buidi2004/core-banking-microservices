# KẾ HOẠCH CHI TIẾT 4 GIAI ĐOẠN PHÂN RÃ HỆ THỐNG VÍ ĐIỆN TỬ (DATABASE-PER-SERVICE - ZERO-CODE)

Tài liệu này đặc tả chi tiết kế hoạch hành động và phương pháp phân tách cơ sở dữ liệu độc lập (**Database-per-Service**) cho cả 5 microservices qua 4 giai đoạn theo mẫu **Strangler Fig Pattern**, đảm bảo **không gián đoạn dịch vụ (Zero-Downtime)** và **không rủi ro mất mát dữ liệu tài chính**.

Nội dung chi tiết đã được cập nhật trực tiếp vào tài liệu kiến trúc dự án tại [EWALLET_5SERVICES_MIGRATION_REPORT.md](file:///home/buidi/app-mono-di-va-khoa/docs/architecture/EWALLET_5SERVICES_MIGRATION_REPORT.md).

## 🗄️ TỔNG QUAN HẠ TẦNG 5 DATABASE ĐỘC LẬP (DATABASE-PER-SERVICE)

Mỗi service sở hữu một cơ sở dữ liệu PostgreSQL và Connection Pool riêng biệt, hoàn toàn độc lập về người dùng quản trị (DB User/Role) và chính sách cấp quyền:

| Service | Cơ Sở Dữ Liệu | Bảng Thuộc Quyền Sở Hữu | Quyền Hạn DB (Role) | Ràng Buộc Khóa Ngoại (FK) |
|---|---|---|---|---|
| **Identity Service** | `ewallet_identity_db` | `users`, `user_profiles`, `user_kycs`, `user_sessions` | Read/Write đầy đủ | Chỉ liên kết nội bộ giữa 4 bảng |
| **Wallet Service** | `ewallet_wallet_db` | `wallets` | Read/Write tối ưu I/O | `user_id` lưu dạng `VARCHAR(36)` (Logical ID, không FK) |
| **Payment Service** | `ewallet_payment_db` | `transactions`, `money_requests`, `banks`, `bank_accounts`, `funding_sources`, `beneficiaries`, `outbox_events` | Read/Write | `source_wallet_id`, `target_wallet_id` lưu `VARCHAR(36)` (Logical ID, không FK) |
| **Ledger Service** | `ewallet_ledger_db` | `journal_entries`, `ledger_postings`, `ledger_accounts`, `audit_logs` | **Append-Only** (Chỉ cấp quyền `INSERT` và `SELECT`, cấm `UPDATE`/`DELETE`) | `transaction_id`, `wallet_id` lưu dạng String |
| **Notification Service** | `ewallet_notification_db` | `notifications`, `device_tokens`, `vouchers`, `promotions`, `support_tickets`, `feedbacks`, `referrals` | Read/Write | `user_id` lưu dạng String |

### GIAI ĐOẠN 1: DỰNG API GATEWAY & TÁCH `NOTIFICATION SERVICE`
> **Mục tiêu:** Thiết lập hạ tầng định tuyến tại tầng biên (Edge Layer) và bóc tách dịch vụ truyền thông, chăm sóc khách hàng. **Rủi ro tài chính: 0%**.

#### 1. Thiết Kế Cơ Sở Dữ Liệu `ewallet_notification_db`:
- **Khởi tạo schema Flyway riêng:**
  - Tách các bảng từ `V1__init_schema.sql`, `V2__add_extended_modules.sql`, `V12__create_device_tokens_table.sql`:
    - `notifications`, `device_tokens`, `vouchers`, `promotions`, `support_tickets`, `feedbacks`, `referrals`.
- **Cắt bỏ khóa ngoại:**
  - Bảng `device_tokens`: Cột `user_id` kiểu `VARCHAR(36)` thay vì `REFERENCES users(id)`. Tạo index: `CREATE INDEX idx_device_tokens_user_id ON device_tokens(user_id)`.
  - Bảng `notifications`: Cột `user_id` kiểu `VARCHAR(36)`. Tạo index: `CREATE INDEX idx_notifications_user_id_created ON notifications(user_id, created_at DESC)`.

#### 2. Kế Hoạch Di Chuyển Dữ Liệu (Data Migration):
- **Bước 1.1:** Chạy snapshot export dữ liệu các bảng notification từ database monolith sang `ewallet_notification_db`.
- **Bước 1.2:** Triển khai độc lập service `notification-service` (cấu hình kết nối tới `ewallet_notification_db`).
- **Bước 1.3:** Đăng ký consumer [NotificationConsumer](file:///home/buidi/app-mono-di-va-khoa/backend/src/main/java/com/fintech/wallet/infrastructure/amqp/consumer/NotificationConsumer.java) lắng nghe RabbitMQ exchange `wallet.exchange`.

#### 3. Cấu Hình Định Tuyến API Gateway:
- Định tuyến các prefix sau về `notification-service:8085`:
  - `/api/v1/notifications/**`
  - `/api/v1/devices/**`
  - `/api/v1/support/**`
  - `/api/v1/feedback/**`
  - `/api/v1/promotions/**`
  - `/api/v1/referrals/**`
- Toàn bộ các API còn lại tiếp tục giữ nguyên chuyển về Monolith cũ (`monolith:8080`).

#### 4. Kịch Bản Kiểm Tra & Rollback:
- **Kiểm tra (Verification):** Gửi 1 giao dịch chuyển tiền trên Monolith $\rightarrow$ Kiểm tra Outbox Event được publish $\rightarrow$ `notification-service` nhận event và bắn thành công FCM Push tới điện thoại di động và thông báo qua WebSocket.
- **Rollback:** Nếu `notification-service` gặp sự cố, chỉ cần sửa cấu hình route trên API Gateway trỏ ngược lại Monolith cũ (mất dưới 30 giây).

### GIAI ĐOẠN 2: TÁCH `GENERAL LEDGER & AUDIT SERVICE`
> **Mục tiêu:** Tách rời toàn bộ khối dữ liệu kế toán tài chính và nhật ký kiểm toán, đảm bảo luồng giao dịch chính không bị chậm do I/O ghi sổ cái.

#### 1. Thiết Kế Cơ Sở Dữ Liệu `ewallet_ledger_db`:
- **Khởi tạo schema Flyway riêng:**
  - Bảng: `journal_entries`, `ledger_postings`, `ledger_accounts`, `audit_logs` (tách từ `V1__init_schema.sql` và `V10__add_idempotency_keys.sql`).
- **Bảo mật và tính toàn vẹn (Append-Only):**
  - Cấp quyền cho user ứng dụng: `GRANT SELECT, INSERT ON ALL TABLES IN SCHEMA public TO ledger_app_user`.
  - Tuyệt đối **REVOKE UPDATE, DELETE** để đảm bảo tính bất biến của chứng từ kế toán.
- **Khóa logic:** `journal_entries.transaction_id VARCHAR(36)` liên kết logic với ID giao dịch bên Payment Service.

#### 2. Kế Hoạch Di Chuyển & Chạy Song Song (Dual-Run / Shadow Run):
- **Bước 2.1 (Backfill):** Đồng bộ toàn bộ dữ liệu lịch sử từ bảng `journal_entries`, `ledger_postings`, `audit_logs` sang `ewallet_ledger_db`.
- **Bước 2.2 (Chạy song song 3 ngày):**
  - Cấu hình RabbitMQ cho phép cả 2 consumer cùng nhận event giao dịch:
    - Consumer 1: Nằm trên Monolith (vẫn ghi vào DB cũ).
    - Consumer 2: [LedgerConsumer](file:///home/buidi/app-mono-di-va-khoa/backend/src/main/java/com/fintech/wallet/infrastructure/amqp/consumer/LedgerConsumer.java) nằm trên `ledger-service` mới (ghi vào `ewallet_ledger_db`).
  - Định kỳ chạy job đối soát tự động: So sánh tổng phát sinh Nợ/Có giữa 2 database. Nếu số liệu khớp 100%, tắt consumer trên Monolith.
- **Bước 2.3 (Cắt chuyển API):**
  - Gateway chuyển route `/api/v1/ledger/**` và các API truy vấn sao kê của [TransactionQueryController](file:///home/buidi/app-mono-di-va-khoa/backend/src/main/java/com/fintech/wallet/presentation/controller/TransactionQueryController.java) sang `ledger-service:8084`.

#### 3. Tiêu Chí Nghiệm Thu:
- Không còn bất kỳ câu lệnh ghi sổ cái nào chạy trực tiếp trong transaction của Monolith.
- Báo cáo sao kê đối soát cân bằng tuyệt đối: $\sum \text{Debit} = \sum \text{Credit}$.

### GIAI ĐOẠN 3: TÁCH `IDENTITY & AUTH SERVICE`
> **Mục tiêu:** Tách định danh người dùng, hồ sơ eKYC, phân quyền và xác thực JWT tập trung tại API Gateway.

#### 1. Thiết Kế Cơ Sở Dữ Liệu `ewallet_identity_db`:
- **Khởi tạo schema:**
  - Bảng: `users`, `user_profiles`, `user_kycs`, `user_sessions` (từ `V1`, `V3`, `V7`).
- **Tách Redis:**
  - Cấp phát Redis DB riêng hoặc namespace cách ly: `identity:otp:*`, `identity:session:*`, `identity:blacklist:*`.

#### 2. Cơ Chế Xác Thực Tập Trung Tại API Gateway:
- **Client $\rightarrow$ API Gateway:**
  - Gửi request kèm `Authorization: Bearer <JWT>`.
- **API Gateway:**
  1. Kiểm tra chữ ký JWT bằng Public Key (Asymmetric RSA hoặc HMAC Secret).
  2. Tra cứu Redis kiểm tra token có nằm trong blacklist không (nếu vừa logout).
  3. Sau khi xác thực hợp lệ, Gateway inject các header tin cậy vào request trước khi chuyển tiếp (downstream):
     - `X-User-Id: a3f1...`
     - `X-User-Phone: 0987654321`
     - `X-User-Kyc-Tier: VERIFIED`
     - `X-User-Role: ROLE_USER`
- **Các Microservices Downstream:**
  - Không cần parse JWT phức tạp, chỉ cần đọc `X-User-Id` từ header để nhận diện người dùng.

#### 3. Xử Lý Luồng Tạo Ví Khi Người Dùng Mới Đăng Ký (Event-Driven Onboarding):
- Trong Monolith: Khi đăng ký user, code gọi trực tiếp `walletRepository.save(new Wallet(userId))`.
- Trong Microservices:
  1. User đăng ký thành công tại `identity-service` $\rightarrow$ Lưu vào `ewallet_identity_db`.
  2. `identity-service` xuất bản sự kiện `UserRegisteredEvent(userId, phone, fullName)` vào RabbitMQ.
  3. `Wallet Service` (hoặc Monolith tạm thời) lắng nghe event này và khởi tạo bản ghi ví mới trong `ewallet_wallet_db`.
  4. Nếu tạo ví thành công, phát sinh `WalletCreatedEvent`. Nếu thất bại, kích hoạt cơ chế retry tự động.

### GIAI ĐOẠN 4: PHÂN TÁCH LÕI TÀI CHÍNH: `WALLET-SERVICE` VÀ `PAYMENT-SERVICE`
> **Mục tiêu:** Phân tách ranh giới quan trọng nhất: **Wallet Service** (Quản lý số dư & Lock) và **Payment Service** (Điều phối thanh toán & Saga).

#### 1. Thiết Kế Tách 2 Cơ Sở Dữ Liệu:

##### Cơ sở dữ liệu `ewallet_wallet_db`:
- Chỉ chứa duy nhất 1 bảng: `wallets`.
- Cấu trúc bảng tối giản để đạt hiệu năng ghi và khóa cao nhất:
  - `id (PK)`, `user_id (Indexed, Unique)`, `balance`, `currency`, `status`, `created_at`, `updated_at`.
- Concurrency Control: Giữ nguyên `SELECT ... FOR UPDATE` (Pessimistic Locking) và Redis Lock `wallet:lock:{walletId}`.

##### Cơ sở dữ liệu `ewallet_payment_db`:
- Chứa các bảng: `transactions`, `money_requests`, `banks`, `bank_accounts`, `funding_sources`, `beneficiaries`, `outbox_events`.
- Cắt bỏ hoàn toàn foreign key `source_wallet_id` và `target_wallet_id` trỏ sang bảng `wallets`.

#### 2. Thiết Kế Hợp Đồng Giao Tiếp gRPC (High-Performance & Low-Latency):
Thay vì gọi service Java cục bộ, `Payment Service` gọi sang `Wallet Service` qua giao thức gRPC nhị phân với độ trễ $< 2\text{ms}$:

```protobuf
syntax = "proto3";
package com.fintech.wallet.grpc;

service WalletInternalService {
  rpc DebitWallet (DebitRequest) returns (DebitResponse);
  rpc CreditWallet (CreditRequest) returns (CreditResponse);
  rpc ReserveBalance (ReserveRequest) returns (ReserveResponse);
  rpc ReleaseBalance (ReleaseRequest) returns (ReleaseResponse);
  rpc CheckLimit (LimitCheckRequest) returns (LimitCheckResponse);
  rpc GetWalletByUserId (UserWalletRequest) returns (WalletResponse);
}

message DebitRequest {
  string wallet_id = 1;
  int64 amount = 2;
  string transaction_id = 3;
  string idempotency_key = 4;
}

message DebitResponse {
  bool success = 1;
  int64 balance_after = 2;
  string error_code = 3;
}
```

#### 3. Mô Hình Saga Orchestrator Điều Phối Giao Dịch P2P:

```
[Khách hàng yêu cầu chuyển tiền qua API Gateway]
                         │
                         ▼
             [Payment Service: INITIATED]
                         │
      ┌──────────────────┴──────────────────┐
      │ 1. Gọi gRPC Debit Wallet Người Gửi   │
      ▼                                     ▼
[Debit Thành công]                 [Debit Thất bại (Hết tiền / Khóa)]
      │                                     │
      ▼                                     ▼
[2. Gọi gRPC Credit Ví Người Nhận]    [Cập nhật Transaction: FAILED]
      │                                [Kết thúc giao dịch]
      ├──────────────────┐
      ▼                  ▼
[Credit Thành công]   [Credit Thất bại / Timeout]
      │                  │
      │                  ▼ (Compensating Reversal)
      │               [Kích hoạt Saga Auto-Reversal]
      │               [Gọi gRPC: creditWallet hoàn tiền Ví Gửi]
      │               [Cập nhật Transaction: REVERSED]
      │               [Ghi Outbox: TransactionReversedEvent]
      ▼
[3. Cập nhật Transaction: SUCCESS]
[4. Ghi Outbox: TransactionCompletedEvent]
      │ (Cùng 1 DB Transaction của ewallet_payment_db)
      ▼
[Outbox Relay publish event lên RabbitMQ]
      ├──► [Ledger Service: Ghi sổ cái kép Nợ/Có]
      └──► [Notification Service: Bắn push FCM + WebSocket]
```

#### 4. Kịch Bản Kiểm Thử Chịu Tải & Nghiệm Thu:
- Chạy kịch bản kiểm thử đồng thời (Concurrency Test) với 1.000 luồng chuyển tiền chéo giữa các ví để xác nhận:
  - **Không có Race Condition:** Số dư cuối cùng của các ví khớp chính xác tuyệt đối.
  - **Không mất mát sự kiện:** 100% giao dịch thành công đều có bản ghi sổ cái kép tương ứng bên `ewallet_ledger_db`.
